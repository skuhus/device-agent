# Symbol Technologies 05e0:1701 (CDC)

USB id `05e0:1701`, enumerating as `Symbol Technologies Bar Code Scanner (CDC)`.
Appears on macOS as `/dev/cu.usbmodem<n>`.

## Status

Terminator resolved on 2026-09-06. The unit now transmits **CRLF**. Set
`terminator: "\r\n"` for this model, or reprogram the scanner to CR and change
the config to match; what matters is that the two agree exactly.

The scanner transmits a Symbol Code Character before the data. The agent does
not strip it: the full frame is published and the upstream side decodes it using
the table below. Nothing needs configuring for that.

There is still no config barcode sheet for this model. Adding one is what stops
the next person repeating this session.

## Measurement 1: no terminator (before reconfiguration)

Captured with the agent itself:

```
skuhus-device-agent probe --path /dev/cu.usbmodem1101 --terminator '\r' \
  --log-level debug --log-payloads --duration 120s
```

11 scans, 480 bytes total, across 1D and 2D symbologies.

- **No suffix.** Zero `0x0D` and zero `0x0A` bytes in the whole capture. The
  final byte of every scan is payload. The agent therefore frames nothing and
  reports one `inter_char_timeout` discard per scan, which is the intended
  behaviour rather than a fault.
- **One read per scan.** Each scan arrived in a single read, so the device sends
  its payload as one burst.
- **Two scans merged.** At 09:03:23.822 and 09:03:23.975, two 61-byte scans
  arrived 153ms apart, inside the 200ms inter-character timeout, and were
  buffered into one 122-byte run. With no terminator the agent has nothing to
  split on, so a fast operator produces one corrupt payload from two scans. This
  is the concrete reason a terminator is not optional.

Sample payloads as received, with no bytes removed:

```
A7393481008232
A42154587
P009YPGHPULEQC36OHSX26PJ7HKC2FMC1MV
P00NDJR5O8E6DTSEJBFUO391AF7CWGHARDO
P01https://www.vevor.com/pages/contact-us/TYJDDDK60MMZYWC8CV2
```

## Measurement 2: CRLF, and the corruption a CR config produces

After a suffix was configured, 13 scans were captured with `terminator: "\r"`
still set. Reads were 37 bytes for a 35-byte payload: payload, CR, LF.

The frame split correctly on CR, leaving an orphaned `0x0A` in the buffer which
was discarded 200ms later by the inter-character timeout. That is harmless while
scanning slowly. It is not harmless at speed:

```
09:11:34.740  frame: P00PJAFARMV1Q6RCKI0B6JC4BOLNWC2HYCU
09:11:34.911  frame: <0a>P00Y6VI8V1KTOSPLQX07ZY7N2FYH0E55I1O
```

Two scans arrived 171ms apart, inside the 200ms inter-character timeout. The
previous scan's stray LF had not yet been discarded, so it was prepended to the
next payload. That frame was emitted with `text_valid: true` and is
indistinguishable downstream from a genuine barcode.

The same capture also lost a scan: at 09:11:35.981 a 15-byte resync discard,
because the framer was still resynchronising from the previous stray LF.

So a CR/CRLF mismatch does not fail loudly. It corrupts one payload and drops
another, **only under fast scanning**, which is exactly why section 4.5 calls
this the bug nobody can reproduce. Testing it at a desk, one scan at a time,
shows nothing wrong.

## Symbol Code Character: reference for the upstream decoder

The scanner prefixes every scan with a Symbol Code Character identifying the
symbology, transmitted as part of the data. The agent passes it through
untouched. This table is from Table E-1 of the product reference guide and is
here for whatever decodes the payload upstream.

**The identifier is one character, except the `P0x` family which is three.** The
first character decides: `P` means three, anything else means one.

### Do not match the identifier as a substring

Read it from position 0 and nowhere else:

```
DAP00838418592059   ->  code D (Code 128), data AP00838418592059
```

That payload contains `P00` inside its data. Anything searching for `P00`
rather than reading the first character will mis-split it.

### Observed against this unit

| Frame | Code | Symbology | Data |
|---|---|---|---|
| `A7393481008232` | `A` | UPC/EAN | `7393481008232`, 13 digits, EAN-13 |
| `A42154587` | `A` | UPC/EAN | `42154587`, 8 digits, EAN-8 |
| `K97PAH932721210504` | `K` | GS1-128 | `97PAH932721210504` |
| `K421752417409012002083496719` | `K` | GS1-128 | begins with AI 421, which is variable length |
| `DAP00838418592059` | `D` | Code 128 | `AP00838418592059` |
| `D00573132901858764243` | `D` | Code 128 | `00573132901858764243` |
| `P007QFG3I113FHBTOK4PN4U07M7MEFDM149` | `P00` | Data Matrix | 32 characters |
| `P01https://www.vevor.com/...` | `P01` | QR Code | a URL |

`D00573132901858764243` and `K00573132901874249298` are near-identical strings
from different symbologies. The identifier is the only thing distinguishing a
GS1-128 from a plain Code 128, which is why it is carried rather than discarded.

## Still to capture: a GS1-128 with a group separator

The `K` scans above are GS1-128, so this unit can produce the one case still
covered only by synthesised test data: a payload containing `0x1D`.

`K421752417409012002083496719` begins with AI 421, which is variable length, so
if a further AI follows there should be a `0x1D` between them. Plain text cannot
show it. Capture it with:

```
skuhus-device-agent probe --path /dev/cu.usbmodem1101 --terminator '\r\n' \
  --log-level debug --log-payloads
```

If `1d` appears in the logged hex, save that stream as a testdata capture and
retire `gs1-128-cr.bin`. That byte is the one a text-based implementation
destroys, and it is currently the least well evidenced part of the test suite.
